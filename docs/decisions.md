# Decisions

Three lists: what is settled, what counts as an assumption, what is open. Append new entries at the bottom. Do not renumber.

| E-10 | Agent runtime (O-01): a dedicated lean service in Go. Guideline: the ops agent can do everything an administrator can (read status, logs, events and resources; run commands in containers; change configuration; restart; roll back). The platform API provides these capabilities so that every action stays logged and approvable; going through the API is not a limit on scope. |
| E-11 | `deploy/bootstrap.sh` installs the base services with `kubectl` alone: upstream manifests (cert-manager, CloudNativePG) by server-side apply, Helm charts (authentik, Longhorn) through the Helm controller built into k3s (`HelmChart`). The machine needs nothing but k3s. |

Every browser resolves `*.localhost` without a DNS entry; public wildcard services such as sslip.io fail because of DNS rebind protection. On the VM: own domain and Let's Encrypt (`CELL_TLS=acme`). |
| E-14 | Volumes (A-06 confirmed): Longhorn on the VM with CSI snapshots, one replica per volume. Tested on Ubuntu 26.04.1 LTS. The local cell uses `local-path` without snapshots. |
| E-15 | Target VM (A-12 confirmed): 4 vCPU, 8 GB are enough. The empty cell uses 3.4 GB and leaves 4.5 GB for apps. Measurement in `status.md` under "Cell by command". |
| E-16 | VM acceptance runs locally in Lima (`make vm-test`), without a cloud account. |
| E-17 | Operator (A-03 confirmed): Go with controller-runtime and controller-gen, that is, the Kubebuilder libraries without its project scaffold. Controller tests run with envtest. |
| E-18 | Helm integration (A-07 confirmed): Flux source and helm controllers. The operator writes `OCIRepository` or `HelmRepository` and `HelmRelease`; a post-renderer sets `helm.sh/resource-policy: keep` on all PVCs of the charts so that data survives uninstalling. |
| E-19 | Reference apps (A-09 confirmed): Forgejo (Helm, OIDC), Nextcloud (image, OIDC through `user_oidc` via a start hook), `traefik/whoami` as a stand-in for a custom build (image, login proxy). All three pass the same end-to-end test. |
| E-20 | `App` is cluster-wide, and every app has the namespace `app-<name>`. Removing keeps the data (volumes stay, the database sleeps, the namespace gets the label `retained`); creating the app again takes it over. |
| E-21 | Local cell: pods reach cell hosts through a CoreDNS rewrite to Traefik. libcurl (PHP, curl) always resolves `*.localhost` to loopback; so image apps in `*.localhost` cells get a small loopback bridge as a sidecar (a subcommand of the operator image). Cells with a real domain do not need it. |
| E-22 | Trust in the cell CA: every app namespace holds the ConfigMap `cell-ca`. Image apps get it mounted automatically, Helm apps through their chart values. |
| E-23 | Backups (A-05 confirmed): databases through the CloudNativePG plugin barman-cloud (continuous WAL archive, base backup per backup), volumes through restic jobs, both in the bucket under `<prefix>/apps/<app>/`. The restic snapshot of a backup carries the backup name and the coordinates of the database backup as tags; a fresh cell therefore finds everything from the bucket alone. Retention 30 days. |
| E-24 | The snapshot before a change is a full backup outside the cell, not a Longhorn snapshot. One path for local and VM cells; Longhorn snapshots remain a later speed-up. |
| E-25 | Every database cluster archives to its own WAL archive (`db-<time>`), so a restored one archives to a new one. The owner of the app database is a managed role; its password always follows the cell's secret, also after a restore from another cell. |
| E-26 | Changes run as a `ChangeRequest`: approval (A-10), backup, JSON merge patch on the app spec, health check within `health.timeoutSeconds`, otherwise return to the previous spec plus restore of the backup. At most one change or restore runs per app; removing the app waits until it has finished. A restore stops a Helm app only after Flux has seen the suspended release (`observedGeneration`), because a reconciliation already in progress could otherwise bring workloads back. A failed change sets the app to `NeedsAttention` until a later one succeeds. Source type (`helm`/`image`) and login type cannot be changed (reinstall), and neither can the size of the database and volumes yet (a rollback could not shrink them). A restore also suspends the app's CronJobs and waits until their own jobs have finished. Once the data is back, the operator first configures the app for its current spec (for a rollback, the previous one) before the workloads run again: otherwise the rolled-back version would run on the restored data. For Helm apps, only a release that Flux has rolled out for this spec counts (`deployed`); `observedGeneration` alone is not enough, because Flux also sets it after a failed upgrade. If Flux gives up (`Stalled`), the restore fails without starting the app. On restart, the chart's workloads get the replicas and CronJob suspension that the last rolled-out release specifies (from Helm's release record, with the Kubernetes defaults where the chart sets nothing); the state captured earlier can come from the rolled-back version in a rollback. Other workloads get the captured state, unless someone else has set the field since the stop (field ownership `cell-restore`). Backups hold the app like changes and restores do (the backup of a change runs under its hold), so that a backup never copies data that is being replaced. A deleted running backup is aborted instead of being completed (it only reads, so aborting is harmless); it holds the app until its job has stopped. A deleted running restore, by contrast, runs to completion, because aborting would leave half-replaced data. A database backup is bound to the cluster it was requested for; if a restore replaces that cluster beforehand, the backup fails instead of combining a backup of the old cluster with the WAL archive of the new one. |
| E-27 | The backup key (restic password, `CELL_BACKUP_PASSWORD`) is passed in at setup and must be kept outside the cell; without it there is no restore into a new cell. |
| E-28 | Local backup target: `rclone serve s3` as a container next to the cell, data in `.cell/backup-s3`. It survives `make cell-down` like a bucket at a provider. |
| E-29 | Platform API: a dedicated service `cell-api` in Go, standard library only (`net/http`), running from the operator image. The identity checks tokens itself: authentik's `userinfo` accepts only tokens it issued and still knows, and returns the current groups; in addition, the token's audience (`aud`) must be the API client `cell-api`, so that tokens an app receives for its users do not count here. Result cached for 30 s. Machine logins through client credentials with user name and app password. Roles from groups: `cell-admins` everything, `cell-agents` read and propose, everyone else reads catalog, apps and change log (superseded by E-46: no group, no role; `cell-viewers` reads). The API passes users and groups through to authentik. Contract: `api/openapi.yaml`; every response in the unit tests is checked against it (kin-openapi, tests only). |
| E-30 | Approvals (A-10): every change, including an admin's, is created without a decision and waits; an admin decides through `POST /v0/changes/{name}/approve` or `/reject`, once. Enforced by the admission policy `cell-change-approval`: nobody creates a `ChangeRequest` with a decision or without an approval requirement, and only the API's account records a decision, not even cluster admins. The API's account may not write `App`s. The API sets the risk level, not the requester: access groups only is low, version only is medium, everything else (source, values, resources, subdomain) is high; an installation that takes over the data of a previously removed app of the same name is also high, and the justification says so. |
| E-31 | Install, remove and restore are actions of a `ChangeRequest` (`action`: `update`, `install`, `remove`, `restore`) and go through the same approval, the same backup beforehand and the same log. Install creates the app locked for the change and ends with the first health check; if it does not become healthy, it stays installed for diagnosis. Remove backs up, deletes the app and, with `deleteData`, also its namespace with all data in the cell; backups in the bucket stay. Restore first backs up the current state and always names the backup, so that approvers see what comes back. Access (`access.groups`) is an update with low risk; the operator binds the groups to the application in authentik, new bindings before removing old ones, so that an error never opens the app. |
| E-32 | Ops agent (E-10): a dedicated service `cell-agent` in Go from the operator image, without rights in the cluster (no service account token). The operator creates its account: service account `cell-agent` in authentik, group `cell-agents`, app password once as secret `cell-system/cell-agent`. It works through tasks one after another; its tools are one call each to the platform API (read apps, pods, logs, events, changes, catalog; propose update and installation). Without a model key, tasks wait until an agent with a key runs. If the agent restarts, it ends its running tasks as failed. |
| E-33 | The agent's language model (E-07): Claude Opus 5.5 (`claude-opus-5-5`) through the Messages API with the customer's key (`CELL_LLM_API_KEY`, secret `cell-agent-llm`), effort `high`, at most 40 model calls per task. The model can be swapped through `CELL_AGENT_MODEL`. Library: anthropic-sdk-go with its tool runner; every request sends the whole conversation (no server-side threads), so that tests can use a simple stand-in model. |
| E-34 | Tasks (`Task`, `cell.internal/v1alpha1`): `diagnose` or `package`, created by the operator (one diagnosis per cause that turns an app into `NeedsAttention`) or by an admin (`POST /v0/tasks`). An agent takes one over (`claim`) and ends it with its answer (`finish`). Every other call by an agent names its task in the header `X-Cell-Task`; the API records it as a step in the task before executing it, and rejects it if that is not possible (no running task of this agent, more than 200 steps). Changes that an agent proposes name the task (`spec.task`) and apply only to the task's app. Only admins and agents read tasks, because answers can quote logs. The change log is therefore `ChangeRequest`s and `Task`s together. |
| E-35 | Installation from a manifest (`POST /v0/apps` with `manifest` instead of `catalog`), for example packaged by an agent: high risk, and the cluster checks the manifest before approval (dry run of the `App` object, that is, schema and CEL rules). The API's account may create `App`s for this, but the admission policy `cell-api-dry-run` allows only dry runs; creation still happens only by the operator after approval (E-30). |
| E-36 | MCP gateway (A-08 confirmed): agentgateway v1.7.0 as a single service `cell-mcp` in `cell-system` at `https://mcp.<domain>/mcp`, without agentgateway's Kubernetes controller (no Gateway API resources, one component fewer). The operator writes its configuration (ConfigMap `cell-mcp`) from the apps with `mcp`: one target per app, as soon as it has been healthy, tool names always prefixed with the app name, stateless (a restart loses nothing), a failed app drops out of the list instead of taking the others down. Tokens must come from the identity for the client `cell-mcp` (signature and audience checked); tokens of the API do not count and vice versa. Access as with the app's login: members of `access.groups`, without groups all accounts. Tools of other apps are missing from the list, and the gateway rejects calls to them. The user's token does not go to the app. agentgateway passes on other client headers; so the gateway itself sets those of the login proxy (`X-authentik-*`), which proxy apps may trust: the user name from the token, and it removes the rest. This way no client can pose as someone else toward an app. |
| E-13 | The bootstrap creates the identity's credentials (DB password, secret key, admin password, API token) once and stores them only as secrets in `cell-system`. |
| E-37 | No MVP and no milestones. Development follows need; what runs is in `status.md` with proof. Earlier exclusions (multiple nodes, VPN, build pipeline, UI) no longer apply. |
| E-38 | The console (the cell's administration UI) is built in this repo. Office suite and central UI stay in other repos (E-03). |
| E-39 | Console: Vite, Svelte 5 and TypeScript in `console/`, built in the image (Node stage) and served by `cell-api` at `https://console.<domain>` (folder `/console`, `CONSOLE_DIR`). Because API and console share one origin, the console calls `/v0/...` without CORS; unknown `/v0/` paths stay JSON errors of the API, and the API host has no console. Strict CSP: only own scripts and styles, connections only to the own origin and to the identity, fonts self-hosted. `openapi-typescript` generates the API types from `api/openapi.yaml`, so the console knows only what the contract says. No backend for the console: it uses the same API as the CLI and agents. |
| E-40 | Console login: a dedicated public client `cell-console` in authentik (authorization code with PKCE, one fixed redirect URI, no secret), created by `cell-api` at startup. `GET /v0/login` names endpoints, client and scopes. The API accepts tokens if their audience is one of its own clients (`cell-api`, `cell-console`); tokens from apps and from the MCP gateway are not accepted. Future own clients (mobile, desktop) each get a client in this list, no logic of their own. The console is restricted to `cell-admins` (binding in authentik; since E-46 also `cell-viewers`, read-only), tokens live in `sessionStorage`; when one has expired, the console signs in again, which the identity answers without asking as long as its session is valid. Signing out discards the token and ends the console's session at the provider (OIDC end session); the identity's own session (single sign-on) stays, as with the cell's apps. |
| E-41 | Console look: design tokens in DTCG format in `console/tokens/`, three layers: brand values (`brand.json`, from Sketches through the Figma file Platform Console 02), their meaning per tone (`night.json`, `paper.json`) and what components paint (`components.json`). `scripts/tokens.mjs` turns them into CSS variables, references stay `var()`, so each layer can later be overridden per customer. | E-42 | Cell across several machines (O-23): one k3s cluster, also across sites. The first machine is the server (control), every further one joins as an agent. The traffic between pods is encrypted by the WireGuard built into k3s (`flannel-backend: wireguard-native`), without a central node and without an outside service; the machines must reach each other, since E-57 in a shared network. The machines distribute images among themselves through the mirror built into k3s (`embedded-registry`, Spegel), without a registry: the platform image is called `registry.cell.internal/cell-operator:<tag>` and exists only in the cell. With two machines there is no redundant control (etcd needs three servers for that). Separation stays one cell per customer (A-02), only across more machines. |
| E-43 | Network for people and the company network (O-24, O-05): a peer-to-peer mesh in the style of Tailscale, self-operated in the cell (Headscale for coordination, the usual Tailscale clients). Every cell is its own network and therefore isolated at first; a company can connect it to its other network, but does not have to. The network between the cell's machines (E-42) does not depend on it. |
| E-44 | Machines join through the platform, as they will later at the customer: an admin creates a join key valid for one hour in the console (API `POST /v0/nodes/joins`) and gets a command to run on the new machine. The command downloads everything from the cell itself; the new machine opens the connection on its own, and the cell holds no root access to foreign machines. The key is a k3s bootstrap token (secret in `kube-system`) together with the checksum of the cluster CA. Installation from a distance over SSH can build on this later. How the key is handed over and when it ends: E-64. |
| E-45 | Apps stay in their namespace (O-22). The operator writes a NetworkPolicy `cell-ingress` into every app namespace: the app's pods accept connections only from their own namespace, from the ingress (`kube-system`), from `cell-system` (gateway, operator) and from the database operator (`cnpg-system`). Other apps therefore cannot reach its services directly, and headers of the login proxy arrive only through the ingress or the gateway. The namespace enforces Pod Security `baseline` (no privileged pods, no paths, networks or processes of the machine), no matter who writes the pod. Flux no longer installs Helm charts with its own rights (cluster admin), but as the app's ServiceAccount `helm-deployer`, admin of its namespace only (ClusterRole `admin` through a RoleBinding). Because namespace admins may also write HelmReleases, helm-controller runs with `--default-service-account=helm-deployer` and `--no-cross-namespace-refs=true`: a release without its own account, for example from a chart, also runs only as the `helm-deployer` of its namespace. Agents read and change only the app of their task, including pods, logs and events (E-34). The NetworkPolicy is enforced by the policy controller built into k3s. |
| E-46 | Roles only through groups (O-28). Having an account in the identity does not yet give a role in the platform (`none`): the account may ask `GET /v0/whoami` and otherwise gets 403 with a note on which group it lacks. `cell-viewers` reads everything (apps including spec, changes, backups, events, logs, machines, tasks, users and groups; since E-63 only the state of the cell), `cell-agents` reads and proposes, `cell-admins` may do everything. The console admits `cell-admins` and `cell-viewers` (binding in authentik), viewers see a note that changes need an admin; the API then answers actions with 403. What a new account sees in the office UI stays with O-25 and O-27 |
| E-47 | Backups through a platform gateway (O-11). Only `backup-gateway` in `cell-system` knows the backup target and its credentials; it is `rclone serve s3` with an auth proxy. Every app gets its own key (ID: app name, secret: SHA-256 of gateway key and app name, both derived identically by the operator and the proxy) and with it reaches only `<root>/apps/<app>/` of the target; another app, a wrong secret or a name with `/` or `.` is rejected. barman-cloud and restic keep speaking S3, only against the gateway; the layout in the target stays as in E-23, existing backups remain valid. The target is any rclone remote: S3 (`CELL_BACKUP_S3_*`), a directory on the first machine (`CELL_BACKUP_PATH`, also a mounted share) or an rclone configuration with a section `[target]` (`CELL_BACKUP_RCLONE_CONFIG`, for example SFTP, WebDAV, SMB). The setup creates the gateway key once and keeps it. The platform does the restoring (`Restore`, E-23), the app needs nothing of its own for it. New dependency: rclone 1.76.0, now also in the cell; rclone considers `serve s3` experimental |
| E-48 | Providers and data protection (O-06, O-16, O-17). Customers with stricter requirements get Claude through a cloud provider with an EU region and data processing agreement, or their own model; only the model's endpoint changes for that |
| E-49 | No four-eyes approval (O-12): an admin may approve their own change (separate call, logged). Speed comes first; the change log shows who approved what |
| E-50 | Names (O-03). The platform is called eigen-platform, the office UI eigen-office, the brand Eigen. In code everything stays name-neutral (guardrail 7): the API group stays `cell.internal`. | E-51 | No object storage in the cell (O-02): backups go through the gateway to any target (E-47), also to a directory; no app in the catalog needs S3. Only when an app needs S3 will one be added. | E-55 | Automatic address for cells. A small name service (`cmd/names`, runs in our cell, standard library only) assigns `<name>-<6 characters>.<zone>` including a wildcard and writes the DNS-01 proofs for Let's Encrypt certificates. It speaks the acme-dns API that cert-manager already knows (`acmeDNS` solver) and keeps no state: a cell's token is an HMAC of its label, and DNS says whether a label is taken. Registering needs a key from us; a cell's token writes only under its label. Every host with a proof gets its own A record, because the proof record otherwise takes it out of the wildcard (RFC 4592); a move sets all records of the cell (label `cell` on every record). Exception to "no central service": the name service holds no customer data and controls nothing, a cell runs without it, and its own domain stays possible. Limit: Let's Encrypt issues 50 new certificates per week per registered domain, and all cells of the zone share this. | E-57 | All machines of a cell lie in one shared network (a private network of the provider, a LAN or a customer VPN between sites); from the internet only what people and devices need is reachable. Two addresses per server: `CELL_NODE_IP` in the machines' network (k3s `node-ip`; join on 6443, kubelet 10250, mirror 5001, WireGuard 51820/UDP) and `CELL_INGRESS_IP`, the cell's address (80, 443, 3478/UDP, name service, mesh). Without a setting both are the same (a machine without a private network). k3s no longer gets an external address (`node-external-ip` and `flannel-external-ip` are dropped), WireGuard runs over the interface that carries `CELL_NODE_IP` (`flannel-iface`; without it Flannel would take the default route's interface, that is, the public one). A joining machine takes the source address of its route to the server as `CELL_NODE_IP`, that is, its address in the shared network. Firewall inbound: 80 and 443/TCP as well as 3478/UDP from the internet, nothing else; the ports between the machines only in the shared network (the Hetzner Cloud firewall does not filter private networks, so it is enough to block them publicly). Replaces from E-42 the operation across sites without a shared network. |

| E-59 | Installation like comparable open-source software: one command, `curl -fsSL https://get.eigen-platform.com \| sudo bash`. ## Research notes

As of 2026-11-18. Check again before pinning versions.

- **k3s**: At the end of August 2026 the v1.36 series was current. License Apache 2.0.
  https://jacar.es/en/k3s-vs-k0s-vs-talos-comparison/
- **CloudNativePG**: 1.30.1 was released in September 2026. Backups to object storage go through the Barman Cloud plugin; the variant built in earlier is deprecated.
  https://cloudnative-pg.io/plugin-barman-cloud/
- **MinIO**: The community edition is no longer developed and is archived. For new setups, Garage (AGPLv3) or SeaweedFS (Apache 2.0) come into question.
  https://www.infoq.com/news/2025/12/minio-s3-api-alternatives
- **authentik**: The only one of the three common candidates that provides an LDAP directory itself, and it brings a login proxy for apps without their own login.
  https://www.ssdnodes.com/learn/keycloak-vs-authentik-vs-zitadel
- **agentgateway**: Apache 2.0, at the Linux Foundation, supports MCP and can be operated through the Kubernetes Gateway API.
  https://agentgateway.dev/docs/kubernetes/latest/
- **kagent**: CNCF sandbox project that runs agents as Kubernetes resources and connects tools through MCP.
  https://www.kagent.dev
- **Division of labor between agent and operator**: The pattern "agent judges, deterministic controllers execute" is explicitly recommended for Kubernetes.
  https://thenewstack.io/ai-agents-kubernetes-control/
- **Cloudron manifest** as a model for `app-manifest.md`:
  https://docs.cloudron.io/packaging/manifest and https://docs.cloudron.io/packaging/addons
